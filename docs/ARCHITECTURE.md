# Архитектура

## Компоненты

```
                         ┌──────────────────────────── web (nginx) ───────────────────────────┐
 браузер ─ :8080 ───────▶│ статический сайт (React)    /api, /metrics → api:8000 (SSE без буфера)│
                         └──────────────────────────────────┬─────────────────────────────────┘
                                                            ▼
 биллинг / жюри ─ PUT снимок, POST события ─▶  api (FastAPI, Python 3.12)
                                                 ├─ source.py      проверка снимка (как CHECK-и схемы кейса)
                                                 ├─ db.py          PostgreSQL: схема кейса + таблицы приложения
                                                 ├─ state.py       пересчёт и рассылка событий SSE
                                                 ├─ scoring/       модель: engine.py + features/*.py (подключаются автоматически)
                                                 ├─ routers/       REST API, /metrics, /stream, OIDC
                                                 ├─ simulator.py   события биллинга и перемотка времени
                                                 └─ telegram.py    бот: уведомления и команды
 Prometheus :9090 ─ Bearer METRICS_TOKEN ─▶ api:8000/metrics
 Dex :5556 ◀─ OIDC (браузер — localhost:5556, сервер — dex:5556)
```

## Поток данных и пересчёт

1. Любое изменение — новый снимок (`PUT /api/v1/source/snapshot`), событие (`POST /api/v1/source/events`), перемотка времени, правка настроек — записывается в PostgreSQL в одной транзакции.
2. После записи вызывается `AppState.recalculate()`: снимок и настройки перечитываются из базы, модель считается целиком. На 200 клиентах это 30–50 мс, включая чтение базы; сам расчёт — 0,45 с на 10 000 клиентов и 4,2 с на 100 000 (линейно, `tools/bench.py`, таблица в README).
3. Результат с номером версии хранится в памяти процесса. Все эндпоинты чтения и `/metrics` отдают одну и ту же версию — числа в панели, API и Prometheus всегда совпадают.
4. После пересчёта рассылается событие `recalculated` по SSE (`/api/v1/stream`). Панель получает его и перечитывает данные открытого экрана — без перезагрузки и без опроса раз в N секунд. Telegram-бот получает тот же сигнал и сообщает о клиентах, перешедших в высокий риск.

Изменения сериализуются блокировкой (`write_lock`): чтение → запись → пересчёт идут по одному, гонок между событиями и правкой настроек нет.

## Хранение

| Таблица | Что хранит |
|---|---|
| `accounts`, `services`, `transactions` | данные источника; схема `001_schema.up.sql` из комплекта кейса без изменений |
| `source_snapshots` | каждый загруженный снимок целиком — для «вернуть к дате снимка» и аудита |
| `status_transitions` | журнал смен статусов услуг (источник: snapshot / event / simulator) — факт оттока |
| `model_settings` | каждая версия настроек модели с автором и списком изменений; действующая — последняя |
| `activity_log` | лента изменений для экрана «Данные» |
| `app_users`, `app_sessions` | пользователи и сессии (хранится только SHA-256 токена) |
| `telegram_subscribers` | чаты, подключённые к уведомлениям |
| `score_history` | изменения score клиентов (пишутся только при изменении) — история в карточке |

Миграции — SQL-файлы в `api/migrations`, применяются при старте и отмечаются в `schema_migrations`.

## Безопасность

- Все данные клиентов и настройки — только после входа: cookie сессии (`httpOnly`, `SameSite=Lax`) или `Authorization: Bearer`. Это проверяет тест на каждый эндпоинт.
- Пароли — scrypt с солью; токены сессий — случайные 256 бит, в базе только хеш; выход удаляет сессию.
- Ограничение входа: не больше 5 неудачных попыток в минуту на пару «логин + адрес».
- CSRF: изменяющие запросы с заголовком `Origin` чужого сайта отклоняются (403); клиенты API без `Origin` проходят по Bearer-токену.
- Одновременная правка настроек: `PATCH /api/v1/model/settings?expectedVersion=N` возвращает 409, если настройки уже изменил другой пользователь — панель передаёт версию автоматически.
- OIDC: Authorization Code Flow с PKCE (S256), проверкой подписи `id_token` по ключам провайдера, `iss`, `aud`, `exp`, `nonce` и `state`.
- `/metrics` — по отдельному токену сборщика или сессии; Swagger открыт, но без данных.
- Секреты — только в переменных окружения (`.env` в `.gitignore`), в репозитории демо-значения для локального запуска.
- Telegram-бот показывает данные только чатам, подключённым кодом доступа.

## Расширяемость

- **Признак** — один файл с классом в `api/app/scoring/features/`: реестр находит его сам (пример в README). Вес автоматически появляется в настройках, API, на экране «Модель», в причинах и пересчёте. Сохранённые настройки получают вес по умолчанию; если признак удалить из кода, его старый вес просто игнорируется.
- **Метрика** — `RadarCollector.collect()` в `routers/metrics.py`.
- **Источник данных** — любой процесс, который шлёт `PUT /api/v1/source/snapshot` или `POST /api/v1/source/events`.
- **Получатель уведомлений** — подписчик `AppState.listeners` (так подключён Telegram-бот).

## Почему так

| Решение | Почему |
|---|---|
| Полный пересчёт вместо инкрементального | проще и надёжнее, укладывается в десятки миллисекунд; нет рассинхронизации между API, панелью и метриками |
| SSE, а не WebSocket | поток только от сервера к клиенту, работает через обычный HTTP и nginx, автоматически переподключается |
| PostgreSQL со схемой кейса без изменений | жюри видит свою структуру данных; настройки и журналы переживают перезапуск |
| Результат расчёта в памяти одного процесса | для объёма кейса достаточно; при нескольких экземплярах результат можно вынести в общий кэш, а события — в LISTEN/NOTIFY PostgreSQL |
